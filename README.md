# Drishti Backend

**Drishti — Healthcare PHI Risk Intelligence Platform.** A multi-tenant API tracking the assets, vendors, identities, threats, controls, policies and remediations that make up an organization's PHI risk posture, and scoring that risk with one auditable formula.

Node 22 + TypeScript + Express 5 + Prisma 7 + Postgres. 97 distinct paths / 121 method+path operations (see `openapi.json`, regenerated by `npm run openapi:generate`; `docs/engineering/ROUTE_INVENTORY.md` is the human-readable version with permission/scoping/audit columns per route).

> **Naming.** The product was renamed from MedGuard to Drishti. Customer-facing names (API title, logs, health response, docs) say Drishti. Database names (`medguard_dev`, `medguard_test`), the npm package name and the Git remote deliberately still say MedGuard — renaming those is a coordinated migration, not a find-and-replace, and nothing in the data model carries the brand. A pre-rename session-cookie name is still *cleared* on logout (never read as credentials — see Security below) so an old browser session isn't left holding a stale cookie.

## Architecture

- **Tenancy**: every scoped query filters on `organizationId`, taken only from the verified session token (`src/lib/tenant.ts`'s `scope(ctx)`) — never from a path, query, or body parameter. Generatively tested (`tests/integration/generated-tenant-isolation.test.ts`): a rival org's rows 404, never leak into a list, and a body-supplied `organizationId` is ignored.
- **Auth**: bcrypt-hashed passwords, a short-lived JWT access token (`Authorization: Bearer`, held in memory on the client only — never a cookie), an httpOnly refresh-token cookie with rotation and reuse-detection, optional TOTP MFA. Full contract in `docs/engineering/FRONTEND_HANDOFF.md`.
- **RBAC**: a genuine permission matrix (`src/lib/permissions.ts`), not per-route role arrays — ADMIN configures the estate, ANALYST assesses within it (plus a field-scoped exception on controls), VIEWER reads.
- **Risk engine**: `score = likelihood × impact × exposure × controlGap / 625 × 100`, each input 1–5, bands LOW (≤20) / MODERATE (≤40) / HIGH (≤60) / CRITICAL (≤80) / EXTREME (>80). `exposure`/`controlGap` are derived automatically from observable facts (PHI volume, access breadth, encryption, open threats, control coverage) and recompute automatically when those facts change; `likelihood`/`impact` stay assessor judgement. The maths (`src/services/riskScoring.ts`) imports no database, so it's unit-testable (including fast-check property tests: score always in [0,100], deterministic, monotonic) without Postgres.
- **Audit**: every mutating handler calls `recordAudit` (enforced by `tests/audit-coverage.test.ts`); `AuditEvent` rows are append-only by a DB trigger *and* a SHA-256 hash chain (`GET /api/audit/verify` walks it) — two independent checks, not one.
- **Everything else**: reports (JSON/PDF/CSV), a PHI inventory view, members/invites/MFA/sessions, per-org configurable thresholds, notifications generated by a daily cron sweep, CSV exports (formula-injection-escaped) on every list endpoint, and an API-key-authenticated ingestion endpoint reusing the same CSV-import validation pipeline.

## Local setup — no Docker (the default path)

```bash
cp .env.example .env            # fill in DATABASE_URL if you're not using the default
brew install postgresql@16 mailpit
brew services start postgresql@16
npm install
npm install-scripts approve prisma @prisma/engines esbuild   # npm 11+ blocks these by default; see "Fresh-clone gotchas" below
npm run setup                   # creates the database if missing, migrates, seeds the Meridian demo data
npm run dev                     # http://localhost:4000
```

`npm run setup` is one command for everything a fresh clone needs; it fails loudly and names the problem (no `DATABASE_URL`, Postgres unreachable) rather than half-succeeding. See `scripts/setup.ts`.

## Local setup — with Docker

```bash
cp .env.example .env            # fill in POSTGRES_PASSWORD and JWT_SECRET
docker compose up -d postgres mailpit
docker compose run --rm migrate   # prisma migrate deploy — not part of `up`, see docker-compose.yml's comment
docker compose up api
```

`docker-compose.yml` is kept for people who have Docker working; nothing locally requires it — see `DEPLOYMENT.md`'s Docker section for the full walkthrough, including why `migrate` is a separate opt-in profile rather than part of `up`.

### Fresh-clone gotchas

**1. `npm install-scripts approve prisma @prisma/engines esbuild` — before anything else works.** npm 11+ blocks package install scripts by default. Without the approval, `npm install` reports success but never downloads the Prisma query engine or the esbuild binary, so `node_modules/.bin` comes up empty and every `prisma`/`vitest` command fails. The only hint is an `npm warn install-scripts` line buried in the install output.

**2. `npx prisma generate` (done for you by `npm run setup`, but required again after any schema change).** The Prisma client is generated output; `src/generated/` is gitignored and not in the repo. Skipping this fails at import time (`Cannot find module '.../src/generated/prisma/client.js'`), not at install time.

### Why the connection URL isn't in `schema.prisma`

Prisma 7 doesn't read it from there. It comes from `prisma.config.ts` for CLI commands (migrate, seed) and from the `@prisma/adapter-pg` driver adapter in `src/lib/prisma.ts` at runtime — both off the same `DATABASE_URL`.

## Environment variables

See `.env.example` for the full, commented list. The ones every environment needs:

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | yes | `postgresql://user@host:5432/dbname?schema=public`. Must contain "test" for anything the test suite touches, "demo" for anything `db:demo:reset`/`db:e2e:reset` touch — both guards refuse otherwise (see `tests/setup/globalSetup.ts`, `scripts/e2e-reset.ts`). |
| `JWT_SECRET` | yes | 32+ random characters. The server refuses to boot without one. Rotating it invalidates access tokens immediately, not refresh tokens — see `docs/engineering/RUNBOOK.md`. |
| `DEMO_USER_PASSWORD` | for any seed command | Shared password for every demo account the seeds create. Never printed by any seed script. |
| `FRONTEND_ORIGIN` | yes | Comma-separated allow-list for CORS; never a wildcard (required for `credentials: true`). |
| `PORT` | no | Defaults to 4000. The server now fails loudly (exits 1, names the port) if it's already taken, instead of silently not binding — see `src/server.ts`. |
| `MAILPIT_URL` | for tests only | Defaults to `http://127.0.0.1:8025`. The test suite starts Mailpit itself if it isn't already running (`tests/setup/globalSetup.ts`). |
| `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASSWORD` | production, for real email | Defaults to Mailpit (`localhost:1025`) everywhere else. |
| `BOOTSTRAP_ORG_NAME`/`BOOTSTRAP_ORG_SLUG`/`BOOTSTRAP_ADMIN_EMAIL`/`BOOTSTRAP_ADMIN_PASSWORD` | only for `db:seed:bootstrap` | A real (non-demo) install's first org + admin. All four must be set or it refuses to run. |

### Two demo datasets — don't mix them up

| Command | Organization | Destructive? | Production guard |
|---|---|---|---|
| `npm run db:seed` | **Meridian Health System** (slug `meridian`) — the CEO-walkthrough demo: `admin@meridian.org` / `f.alrashid@meridian.org` / `a.patel@meridian.org`, plus `admin@wayam.ai` / `analyst@wayam.ai` / `viewer@wayam.ai` as aliases on the same org/roles | Yes — truncates and rebuilds every core table | Refuses unless `SEED_ALLOW_PRODUCTION=yes` |
| `npm run db:seed:demo` | **Drishti Demo Healthcare** (slug `drishti-demo`), upsert-only | No | Refuses unless `DEMO_SEED_ALLOW_PRODUCTION=yes` |
| `npm run db:demo:reset` | Drishti Demo Healthcare only — deletes and re-seeds just that org, backs up the database first | Scoped-destructive (one org) | Refuses unless the database name contains "demo" |
| `npm run db:e2e:reset` | Meridian Health System, truncate + rebuild, fast | Yes, by design — meant to run between E2E test files | Refuses `NODE_ENV=production` *and* any database name not containing "test" |
| `npm run db:seed:bootstrap` | Whatever org/admin you name via `BOOTSTRAP_*` env vars | No | Refuses to run at all without all four env vars set |

**There is no scoped reset for Meridian during a live demo** — `db:demo:reset` only ever touches Drishti Demo Healthcare. Resetting Meridian mid-demo means re-running `npm run db:seed` (full rebuild) or, for an E2E/CI context specifically, `npm run db:e2e:reset`.

## Authentication

```bash
curl -X POST http://localhost:4000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@wayam.ai","password":"<DEMO_USER_PASSWORD>"}'
```

The access token comes back **only** in the response body — never as a cookie. A client holds it in memory and sends `Authorization: Bearer <token>` on every request. Only the refresh token is ever a cookie (httpOnly, with rotation and reuse-detection), and the two cookie-authenticated endpoints that use it (`/auth/refresh`, `/auth/logout`) additionally require an `X-Drishti-Csrf` header. Full contract, including the MFA two-call shape and session-expiry handling, is in `docs/engineering/FRONTEND_HANDOFF.md`.

### Swapping in a hosted auth provider later

`requireAuth` depends on exactly one thing: `verifyToken(token)` returning an `AuthUser`. Moving to a hosted provider means reimplementing that one function against its SDK and deleting the login route — no other route handler changes.

## Security

See `docs/engineering/SECURITY_REVIEW.md` for the full OWASP ASVS Level 2 walkthrough. Summary: `helmet` on every response; CORS is an explicit allow-list with `credentials: true`, never a wildcard; CSRF header on the two cookie-authenticated routes; rate limits keyed **per user** (not shared IP — see `FRONTEND_HANDOFF.md`'s table and the 30s-polling-budget derivation) for authenticated traffic, per-IP only for the handful of pre-authentication routes (login, forgot-password, reset-password, accept-invite); bcrypt cost 12 in production; log redaction covering every credential/secret field; a ZAP dynamic scan runs in CI on every push to this branch's PR.

## Risk scoring

`score = likelihood × impact × exposure × controlGap / 625 × 100`, each input 1–5. Bands: ≤20 LOW · ≤40 MODERATE · ≤60 HIGH · ≤80 CRITICAL · >80 EXTREME. The curve is steep by construction — a product of four factors means a 4/4/4/3 assessment lands at only 30.72, and EXTREME needs a raw product of 506+ (effectively all 5s).

`src/services/riskEngine.ts` is the entry point callers import; the pure maths lives in `src/services/riskScoring.ts`, which imports no database (unit-testable, including fast-check property tests, without Postgres). The seed derives its stored scores from the same function, so seeded rows and recomputed rows agree by construction.
