# Frontend Handoff

The single source of truth for the frontend team integrating against the Drishti API. If anything here disagrees with `openapi.json` (committed at the repo root, regenerated by `npm run openapi:generate`), the OpenAPI spec is the one to trust for exact field shapes — this document is the narrative around it.

## Auth contract

### Login

```
POST /api/auth/login
{ "email": "admin@wayam.ai", "password": "..." }
```

Success (200):

```json
{
  "data": {
    "token": "<JWT access token>",
    "expiresIn": 3600,
    "refreshToken": "<64-hex-char token>",
    "refreshExpiresIn": 2592000,
    "user": { "id": 1, "email": "admin@wayam.ai", "role": "ADMIN", "organizationId": 1 },
    "memberships": [ /* every org this account belongs to */ ]
  }
}
```

**The access token lives in memory on the client only — never in `localStorage`, `sessionStorage`, or a cookie.** It is never set as a cookie by the server either. Every authenticated request sends it as:

```
Authorization: Bearer <token>
```

This is a deliberate fix, not the original design: an earlier version of this API also accepted the access token from a cookie, which meant it rode along automatically on any cross-site request with no way to block that the way the refresh/logout CSRF header (below) blocks theirs. If any future response ever sets an access-token cookie again, treat that as a regression, not a feature — see `src/middleware/auth.ts`'s `extractToken` for the enforcement and `tests/integration/generated-auth-gate.test.ts` for the regression test.

### MFA challenge

If the account has MFA enabled, the **same** `POST /api/auth/login` call returns a 401 instead of a token:

```json
{ "error": { "code": "MFA_REQUIRED", "message": "...", "mfaRequired": true } }
```

Call it again with the same `email`/`password` plus `mfaCode` (a TOTP code, or a recovery code):

```
POST /api/auth/login
{ "email": "...", "password": "...", "mfaCode": "123456" }
```

There is no separate "verify MFA" endpoint — it's always a second call to the login endpoint. A wrong code returns another 401 with `MFA_REQUIRED`; the account is not locked out by this (see rate limits below), but each wrong code consumes the login rate-limit budget.

### Refresh

The refresh token is **never held by the frontend as a readable value** for a browser client — it travels only as an `httpOnly` cookie (`drishti_refresh`) the browser already carries automatically. (It's also returned in the login body for non-browser clients — CLI tools, mobile apps, the test suite — which can't rely on a cookie jar; a browser frontend should ignore that field.)

```
POST /api/auth/refresh
X-Drishti-Csrf: 1
```

No body needed for a browser client (the refresh cookie does the work); the CSRF header is mandatory — a bare refresh call with no `X-Drishti-Csrf` header gets 403. The header's value doesn't matter, only its presence; `1` is as good as anything.

**Refresh rotation and reuse detection**: every successful refresh issues a brand-new refresh token and revokes the one just used. If a refresh token is presented a second time (it's already been rotated away), the server treats that as a sign the token was stolen or replayed and revokes **every** refresh token for that user — the user is signed out everywhere, not just on the device that reused the token. The frontend should treat any 401 from `/auth/refresh` as "the session is gone, send the user to login," not "retry."

### Logout

```
POST /api/auth/logout
X-Drishti-Csrf: 1
```

Same CSRF header requirement as refresh, same reason (cookie-authenticated). Clears both the refresh cookie and any (legacy) access-token cookie a very old browser session might still be holding. `POST /api/auth/logout-all` (bearer-authenticated, no CSRF header needed) revokes every session for the account, not just the current one.

### Session expiry behaviour the frontend needs to handle

- Access token expires in 3600s (1 hour). The frontend is responsible for calling `/auth/refresh` before then (or on the first 401 it gets back from any other endpoint) and swapping in the new access token in memory.
- A 401 from any endpoint *other than* `/auth/refresh` usually just means "access token expired, refresh and retry once." A 401 from `/auth/refresh` itself means the session is actually gone — refresh token expired, revoked, or reused — and the frontend should clear its in-memory token and route to login, not loop.
- `GET /api/auth/sessions` lists every active session (device/IP/user-agent, last activity) for a "sign out other devices" screen; `POST /api/auth/sessions/:id/revoke` and `POST /api/auth/sessions/revoke-others` back it.

## Error envelope

Every error response, from every endpoint, is:

```json
{ "error": { "code": "SOME_CODE", "message": "human-readable", "details": {}, "requestId": "..." } }
```

`details` and `requestId` are present on some errors, absent on others — treat both as optional. `requestId` matches the `x-request-id` response header and the backend's own structured logs, so it's worth surfacing in any error-reporting UI for support purposes.

### Status codes to handle specifically

| Status | Meaning | What the frontend should do |
|---|---|---|
| 400 | Validation error (bad body/query/params) | Show the message; it names the field. |
| 401 | Not authenticated, or token expired | Refresh and retry once (see above); if that also 401s, go to login. |
| 403 | Authenticated, but not permitted (wrong role), or a missing CSRF header on refresh/logout | Show a permission error — don't retry. A 403 from a list/detail endpoint for a *resource that doesn't belong to the caller's org* never happens — that's a 404 instead (see below), so a 403 always means "your role doesn't allow this," never "this isn't yours." |
| 404 | Not found — including a real resource that exists but belongs to a different organization | Treat identically to "doesn't exist." The API never distinguishes "doesn't exist" from "exists but isn't yours," by design — see `tests/integration/generated-tenant-isolation.test.ts`. |
| 409 | Conflict (duplicate name, already-archived, invalid state transition) | Show the message; it's specific (e.g. "A policy named X already exists"). |
| 429 | Rate limited | `Retry-After` header is set in seconds; back off and retry after that. Don't show this as an error to the user on ordinary polling — it should never happen under normal use (see rate limits below) and most likely means something is polling too aggressively or stuck in a retry loop. |

## Rate limits

Authenticated routes (everything except login/forgot-password/reset-password/accept-invite) are keyed **per logged-in user**, not per IP — a hospital where every workstation shares one outbound IP does not share one budget. Limits, all per 15-minute window:

| Route class | Limit | Keyed by |
|---|---|---|
| Ordinary authenticated API traffic (assets, risks, vendors, etc.) | 600 req | user |
| CSV/PDF exports (`?format=csv` on any list route, or the dedicated report routes) | 30 req | user |
| Ingestion API (`POST /api/ingest/:recordType`) | 60 req | API key |
| `POST /api/auth/login` | 10 failed attempts (successes don't count) | IP |
| Password reset / invite accept (`forgot-password`, `reset-password`, `accept-invite`) | 20 req | IP |
| `/api/auth/*`'s other routes (`me`, `mfa/*`, `sessions`, `change-password`, `logout-all`) | 300 req | IP (backstop; low-volume, not the polling surface) |

**The polling budget the 600/15min ceiling was sized for**: the dashboard is expected to poll on a 30-second interval, with up to 6 distinct queries per tick for a busy view (risk distribution, assets list, threats summary, remediations summary, notifications unread-count, access summary). That's 900s/30s = 30 cycles per 15-minute window × 6 queries = 180 requests from passive polling alone — the ceiling (600) gives roughly 3x headroom over that for simultaneous manual use (opening detail views, paging, filtering) on top of the background polling. **If a screen needs to poll more than 6 endpoints every 30 seconds, or poll faster than every 30 seconds, say so before shipping it** — the ceiling was sized for a specific pattern, not derived from nothing.

| Command | Org | Password source |
|---|---|---|
| `npm run db:seed` | Meridian Health System — `admin@wayam.ai` / `analyst@wayam.ai` / `viewer@wayam.ai` (also `admin@meridian.org` etc.) | `DEMO_USER_PASSWORD` in `.env` |

## Running the backend locally for frontend E2E tests (no Docker)

```bash
git clone <repo> && cd MedGuard_Shield_Backend
cp .env.example .env            # fill in DATABASE_URL if not using the default
brew install postgresql@16 mailpit
brew services start postgresql@16
npm install
npm run setup                   # creates the DB, migrates, seeds Meridian data
npm run dev                     # http://localhost:4000
```

- **Port**: `4000` by default (`PORT` in `.env`). If something else is already bound to it, the server now fails loudly and names the port — it used to fail silently and let another process on the same machine eat every request (see `src/server.ts`'s `error` handler and `src/server.test.ts`).
- **Mailpit**: invite/password-reset emails land at `http://localhost:8025` (the Mailpit web UI); the backend's own test suite reads them back via `http://localhost:8025/api/v1/messages`, which an E2E suite can reuse the same way.
- **Env vars an E2E runner needs**: `DATABASE_URL` (point it at a dedicated E2E database, not `medguard_dev`), `JWT_SECRET`, `DEMO_USER_PASSWORD`, `FRONTEND_ORIGIN` (must match whatever origin the E2E browser context runs from, for CORS).

### Fast, deterministic reset between E2E runs

```bash
DATABASE_URL="postgresql://$USER@localhost:5432/medguard_e2e_test?schema=public" npm run db:e2e:reset
```

Truncates and reseeds the fixed Meridian dataset in about a second (confirmed: ~1.5s locally, including the Node process startup). `RESTART IDENTITY` keeps every id stable across resets, so an E2E suite can hardcode ids (asset 6 is always "Billing Engine DB", etc. — see `prisma/seed.ts`'s `ASSETS` array for the full list) rather than discovering them fresh every run.

Two guards, stricter than the demo seed itself:
- Refuses `NODE_ENV=production` (same as `db:seed`).
- **Also** refuses any `DATABASE_URL` whose database name doesn't contain `test` — specific to this command, since an E2E suite runs it between every test file and the one way that goes wrong quietly is a misconfigured E2E environment accidentally pointing at a real database. See `scripts/e2e-reset.ts` and its test, `scripts/e2e-reset.test.ts`.
